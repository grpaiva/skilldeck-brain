## The commitments

These are the application's stated core privacy commitments, and they are the strongest thing we have to say on this subject.

<Columns cols={2}>
  <Card title="No video, ever" icon="video-off">
    Skill Deck never records meeting video or audio. Bots are configured transcript-only, with recording format set to `none`.
  </Card>
  <Card title="Transcripts are temporary" icon="clock">
    Raw content, including transcripts, never lives in the database. It sits in a cache that expires after **7 days**.
  </Card>
  <Card title="Residual data is deleted" icon="trash-2">
    A daily job deletes leftover files and calls the bot provider's delete-data endpoint after 7 days.
  </Card>
  <Card title="Only conclusions persist" icon="database">
    What survives is metadata, processing state, evaluations, scores, score history, notifications, and share records.
  </Card>
</Columns>

## What is stored, and for how long

| Data | Where it lives | How long |
| --- | --- | --- |
| Meeting video and audio | Nowhere. Never captured. | — |
| Meeting transcript | Application cache only | 7 days |
| Raw email and conversation bodies | Application cache only | 7 days |
| Residual files and bot-provider data | Temporary storage | Deleted after 7 days by a daily job |
| Evidence metadata (title, type, status, timestamps, participants) | Database | Retained |
| Evaluations, scores, and score history | Database | Retained |
| Moment excerpts from a track | Database | Retained, capped at 500 characters each, maximum 5 per evidence |

The design principle is worth stating explicitly when you explain this: **Skill Deck keeps the conclusions, not the recordings.**

Raw transcript text is never written to a database column. Notifications are explicitly forbidden from containing raw transcript or body content.

## Only your own behavior is evaluated

This is the point that resolves most objections, and it is not widely understood.

> The subject is always the evidence owner. In multi-person meetings, emails, or conversations, agents evaluate only the owner's behavior. Other participants matter only when they clarify the owner's behavior or impact.

A meeting with five people does not produce five profiles. It produces evidence for the Skill Deck user whose calendar scheduled the bot, about that person only. Colleagues appearing in the transcript are context, not subjects.

Related: a **single-participant meeting is marked processed without transcription or evaluation**. There is no behavior with others to observe, so nothing is analyzed.

## What a manager can see

<Note>
  The distinction that matters: a manager sees **the analysis**, not **the recording**.
</Note>

Be accurate about this rather than reassuring. A manager's access is real but deliberately bounded, and the boundaries are drawn in code rather than by convention.

### A manager does see

On their team member's page, in the order the Manager Coaching Playbook has them read it:

- **Overview** — progress against Goal, time on the current Track, and Track history: completed, active, switched, rolled, expired. Plus the number of evaluations in the Cycle.
- **Journal** — the member's Kickoff, Weekly Prep, Weekly Review, and Wrap-Up dispatches, in full.
- **Deck** — current scores and confidence across the member's Skills, the same aggregate view the member sees.
- **Track analyses** — the per-meeting summary for the tracked Skill, including moment excerpts.

Opening a member's Journal post does not mark it read for the member.

### A manager does not see

This list is enforced, not aspirational:

| Hidden from the manager | How |
| --- | --- |
| Meeting video and audio | Never captured |
| Meeting transcripts | Never in the database; gone from cache after 7 days |
| **Evidence Evaluated dispatches** | Explicitly excluded from the manager-visible dispatch list. The post-meeting analysis a member receives is private to them. |
| Individual evidence pages | Owner-only. The evidence page returns a 403 to anyone who is not the evidence owner, including their manager. |
| Click-through from a Track analysis to the underlying evidence | The expand link is disabled for managers |
| The full list of individual evaluations | Not exposed in any manager view |
| The body of a member's development report | The manager sees that a report exists, with no link to open it |
| Benchmarks the member favorited | Private, so a member can hold aspirations their manager does not see |
| Anything through the MCP server | MCP is first-person only. There is no manager, recruiter, or org-level access path. |

<Tip>
  The clean way to say this: **a manager sees the conclusions and the short excerpts behind them, never the meeting and never the raw analysis.** The member gets more detail about themselves than their manager does.
</Tip>

That last point is the strongest thing to say in a privacy conversation, and it happens to be true.

## Model providers

Responses are configured not to be retained on the provider's side. The `OPENAI_STORE` setting defaults to `false` in the application's AI configuration, specifically so that evidence-derived conversations are not stored by the provider.

## Sharing

A user can share a piece of evidence with another user. This is user-initiated, and it is bounded by the same retention rules:

- Sharing only works while the content is still cached, so a share invitation expires no later than 7 days after processing.
- Accepting a share copies content into the recipient's cache, not into the database.
- The copy is re-evaluated for the recipient, with the original triage and evaluation metadata stripped, so the recipient gets their own evaluation rather than inheriting someone else's.

## Answering the surveillance objection

When someone says "this is surveillance", do not argue with the frame. Replace it with facts, in this order:

<Steps>
  <Step title="Nothing is recorded">
    No video and no audio, ever. The bot produces text and nothing else.
  </Step>
  <Step title="The text does not survive">
    Transcripts live in a cache for 7 days and are then gone. They are never written to the database.
  </Step>
  <Step title="Only the user is evaluated">
    A meeting produces evidence about the person whose calendar it came from. Not about their colleagues.
  </Step>
  <Step title="The manager gets the analysis, not the meeting">
    Scores, Track progress, and short excerpts. They cannot open an individual evidence page — it returns a 403 to anyone but the owner — and the post-meeting analysis a member receives is private to them.
  </Step>
</Steps>

Never use the words "surveillance" or "monitoring" about our own product, including when denying the charge. Repeating the frame reinforces it. Describe what the product does instead.
